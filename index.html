Chapter 0

You Have Been Handed a Shovel

Nobody asked whether you wanted one. That is how shovels work.

Somebody has left a gopher in your kitchen.

You didn't order a gopher. But there it is, sitting in your good fruit bowl, wearing a cyan bandana, and it has brought a shovel that is much too large for it and a small laminated card that says HELLO I AM YOUR TEACHER in handwriting that is honestly not great.

The gopher's name is Gord. Gord digs tunnels. He digs them alarmingly fast — this is the entire personality of the language you are about to learn — and he has been sent to teach you Go, which is a programming language invented by three people at a company who were, according to legend, tired of waiting for something to compile.

Go is sometimes called Golang, because "go" is a difficult thing to type into a search box. Nobody who uses it calls it that out loud. They just say Go, and then, if pressed, they say it again louder.

Here is what Gord believes, deep in his small round chest:

A tunnel should be boring. A tunnel should be so boring that a stranger can walk into it in the dark and not be surprised by anything. Surprises in tunnels are how you end up in someone's basement.

This is Go's whole disposition. Other languages will offer you eleven elegant ways to say one thing, and you will spend a pleasant afternoon choosing between them. Go offers you one way, which is slightly ugly, and then it puts a hand on your shoulder and walks you away from the argument.

You may resent this for about three weeks. Then one day you will open a stranger's Go code and read it at a glance like a road sign, and you will feel a strange grudging warmth, and Gord will already be gone, and there will be dirt on your counter.

What you need before we start

  • Go, installed from go.dev/dl. It is one download. It does not ask you questions.
  • Any text editor you already like.
  • A terminal, in which we will type things and be pleased.
  • Optionally: the Go Playground, a website that runs Go for you, so you can put this whole guide off until Thursday.
Chapter 1

Hello, Dirt

The smallest possible tunnel, and the ritual for entering it.

Gord drags a folder onto your desk with his teeth. Make one too. Call it tunnel. Go inside it and say this to your terminal:

$ mkdir tunnel && cd tunnel $ go mod init example.com/tunnel go: creating new go.mod: module example.com/tunnel

You have just declared a module, which is Go's word for "this pile of files is one pile." The name looks like a website because someday it might be one; for now it is a fib everyone has agreed to accept.

Now a file called main.go:

package main import "fmt" func main() { fmt.Println("hello, dirt") }
press the stamp

Four things happened there, and Gord would like to point at each of them with the shovel.

package main is the gopher saying "this tunnel has a front door." Every Go file belongs to a package; the package named main is the special one that becomes a program you can actually run. Any other name makes a library — a tunnel with no entrance, which other tunnels connect to.

import "fmt" fetches a crate from the standard library. It's pronounced "fumpt" by absolutely nobody and "format" by everyone. It does printing. Go's standard library is unusually large and unusually good, and a fair amount of learning Go is just discovering that the thing you were about to write is already in there, sitting quietly, tested.

func main() is where the program starts. When main returns, your program is over. Gord finds this very restful.

Those aren't spaces, they're tabs, and no you don't get to have an opinion. Run gofmt (or go fmt ./...) and the formatting argument ends forever. Every Go project on earth looks the same. It is the most peaceful war ever won.

And go run . compiles the whole thing and runs it in one breath. When you want the actual finished burrow — a single self-contained binary you can hand to a stranger — you say go build instead, and out drops one file with no runtime to install alongside it. This is the trick that made Go popular with people who deploy things at 2am.

Chapter 2

Nib the Compiler Is Not Angry, Merely Tidy

Variables, types, zero values, and one bird with strong feelings about turnips.

There is a heron standing in your hallway.

Nib does not compile your program. Nib declines your program.

His name is Nib and he is the compiler. He wears a monocle he does not need. He is holding a clipboard and he is going to refuse to build your program over things you consider trivial, and in about a month you will realise he has been doing you favours the entire time.

Here is Nib's most famous grievance. You declare a variable, you never use it, Nib will not proceed:

func main() { turnips := 4 // declared and not used: turnips fmt.Println("nothing about turnips") }

Every other language shrugs at this. Nib treats an unused variable as evidence that you changed your mind halfway and forgot to tell anyone. He is usually right. Same for imports you don't use — delete them, or Nib stands in the doorway.

The two ways to name a thing

var depth int = 30 // the long way, with the type spelled out var depth2 = 30 // type inferred: int depth3 := 30 // short way. only works inside a function const maxDepth = 200 // fixed at compile time, forever

You'll use := almost always. Gord uses it for everything, including his taxes.

Zero values, or: nothing is ever empty

This is the loveliest thing about Go and hardly anyone mentions it. A declared variable is never garbage and never undefined. It starts at the zero of its kind, immediately, always:

var n int // 0 var s string // "" (an empty string, not nil) var ok bool // false var f float64 // 0 var p *Gopher // nil — a signpost pointing at no gopher at all

So a fresh Gopher struct isn't a hollow shell to be filled in later; it's a real gopher with no name, no mood, and an empty pouch. Whole categories of nervous initialisation code just evaporate.

Types in Go don't convert themselves out of politeness. An int will not quietly become a float64 for you. Say float64(n) and mean it. Nib is watching.

Ifs and fors, and that's the lot

Go has one loop. It is called for. It wears several hats:

for i := 0; i < 3; i++ { } // the classic for depth < 200 { depth++ } // the "while" hat for { break } // forever, until it isn't for i, thing := range pouch { } // over a collection if depth > 100 { fmt.Println("that's plenty") } else { fmt.Println("keep going") }

No parentheses around the condition. No while, no do-while, no unless. There is a switch and it's genuinely nice — it doesn't fall through unless you beg — but that's the whole control-flow shelf. You can now read the loops in every Go program ever written. Sorry it wasn't more of an adventure.

Chapter 3

Everything Hands You Two Things

Functions, the second thing, and the small damp envelope named err.

In most languages, when something goes wrong, the function panics like a startled bird and hurls an exception up through the ceiling, and somewhere three floors above, someone catches it, or doesn't.

Go does not do this. In Go, when something goes wrong, the function turns around, and hands you a small damp envelope.

Functions can return more than one value, and by long tradition the last one is the envelope:

func dig(cm int) (int, error) { if cm > 40 { return 0, fmt.Errorf("hit a pipe at %d cm", cm) } return cm, nil }

And on the other side, the ritual. You will type this ten thousand times. Gord types it in his sleep. Some people complain about it in blog posts; Gord reads those blog posts and says nothing, and digs.

moved, err := dig(41) if err != nil { fmt.Println("well:", err) return } fmt.Println("dug", moved, "cm")

Here is the argument for the ritual, and it's better than it looks. An error in Go is an ordinary value. It sits in a variable. It is passed around, wrapped, logged, ignored on purpose. There is no invisible second control-flow system running through your program behind a curtain. Every place a thing can go wrong is a place with three visible lines of code in it. Your program becomes long and extremely honest.

Wrap an envelope inside a bigger envelope with %w:
fmt.Errorf("digging: %w", err)
Later, errors.Is and errors.As can reach back inside and find the original.

defer: the promise you make on the way out

Gord, on entering a room, always says aloud what he will do when he leaves. Then he forgets about it entirely, and it happens anyway.

func visit() { f, err := os.Open("tunnel.txt") if err != nil { return } defer f.Close() // runs when visit() ends, no matter how it ends // ... twelve branches, three returns, one panic ... }

A deferred call runs when the surrounding function finishes — normal return, early return, or a full-blown panic. Put the cleanup right next to the thing that needs cleaning, one line later, and then stop thinking about it. It's the single most agreeable feature in the language.

panic, briefly, and then let's not

Go does have a panic. It is for when the tunnel has collapsed and there is no sensible next step — a bug, not a bad day. It unwinds, runs your defers, and prints a stack trace. There's a recover to catch it, mostly used at the very top of long-lived servers to keep one bad request from taking the building down.

Do not use panic as your envelope. Nib will not stop you. Nib will simply think less of you, silently, forever.

Chapter 4

A Gopher Is a Small Box of Drawers

Structs, methods, and the difference between a gopher and a note about where a gopher is.

Go has no classes. There is no inheritance, no extends, no eight-generation family tree of AbstractBaseRodent. There is a struct, which is a box with labelled drawers, and there are functions you can bolt onto it.

type Gopher struct { Name string Depth int Pouch []string } gord := Gopher{Name: "Gord", Depth: 12} fmt.Println(gord.Name, gord.Depth, len(gord.Pouch)) // Gord 12 0 — Pouch is nil, and len(nil) is a peaceful 0
Capitalisation is the access modifier. Name is visible to other packages; name is private to this one. That's it. That's the whole keyword-free privacy system.

Methods are just functions with a little hat

func (g Gopher) Greet() string { return g.Name + " says CHEEKFULS!" } func (g *Gopher) Stuff(thing string) { g.Pouch = append(g.Pouch, thing) } fmt.Println(gord.Greet()) // Gord says CHEEKFULS! gord.Stuff("one bolt") // gord now genuinely has a bolt

The bit in parentheses before the name is the receiver. And now the one thing in this chapter you must actually hold in your head:

(g Gopher) receives a photocopy of the gopher.
(g *Gopher) receives directions to the actual gopher.

Write to a photocopy and your changes are thrown in the bin the moment the function ends. That's why Stuff takes a pointer — it's rummaging in the real pouch. Greet only reads, so a photocopy is fine.

Go is kind here: you don't have to remember arrows. Write gord.Stuff("bolt") and the compiler quietly takes the address for you. Rule of thumb: if any method on a type needs a pointer receiver, give them all pointer receivers, for the same reason you don't put one drawer handle on upside down.

A *Gopher that points nowhere is nil. Reach into a nil pointer's drawers and the program panics. Nil is Go's one genuinely sharp corner — mind it and you'll be fine.

Embedding, which is not inheritance no matter how much it looks like it

type Mammal struct { Legs int } func (m Mammal) Walk() string { return "padding along" } type Gopher struct { Mammal // no field name — this is embedding Name string } g := Gopher{Mammal: Mammal{Legs: 4}, Name: "Gord"} fmt.Println(g.Legs, g.Walk()) // 4 padding along

The outer type borrows the inner one's fields and methods without pretending to be it. Go calls this composition, and it is deliberately less powerful than inheritance, and that is the entire point.

Chapter 5

Cheek Pouches

Slices and maps: the only two containers you will use for years.

A slice is a growable list. It is what you reach for roughly always. Behind it sits a fixed-size array, which you will almost never touch directly, the way you almost never touch the studs behind a wall.

pouch := []string{"acorn", "bolt"} pouch = append(pouch, "one sock") // note: you must reassign fmt.Println(len(pouch), pouch[0]) // 3 acorn fmt.Println(pouch[1:]) // [bolt one sock] for i, thing := range pouch { fmt.Println(i, thing) }

That reassignment is not decoration. append may need more room than the pouch has; when it does, it quietly moves everything into a bigger pouch and hands you a new one. Throw away the return value and you throw away the move. If you know how much you're about to stuff in, say so up front:

pouch := make([]string, 0, 8) // length 0, room for 8 before it moves house

Maps: the labelled shelf

counts := map[string]int{} counts["acorn"]++ counts["acorn"]++ n := counts["radish"] // 0 — missing keys give the zero value n, ok := counts["radish"] // 0, false — the two-value form knows the truth delete(counts, "acorn")

That ok is how you tell "not there" apart from "there, and zero." The two-value read is the whole trick, and it shows up all over Go: a value, and a small quiet second thing telling you whether to trust it.

Ranging over a map gives you the keys in a deliberately random order every single run. The language does this on purpose, so you can never accidentally depend on it. Want order? Collect the keys into a slice and sort.Strings them.

One trap, and it's a real one: a map declared with var m map[string]int is nil. You can read from it happily forever. Write one key to it and the program panics. Use map[string]int{} or make(map[string]int) and it never comes up again.

Chapter 6

The Duck Who Signs Nothing

Interfaces, and the best idea in the language.

A duck has been standing at the end of the tunnel for some time.

It never agreed to anything. It simply quacks, and so it qualifies.

An interface in Go is a list of behaviours. Not a class to inherit, not a contract to sign — just a list, written down somewhere, of what a thing must be able to do.

type Digger interface { Dig(cm int) string }

Now here is the part that makes people sit up. Nobody has to declare that they implement it. There is no implements Digger. If a type happens to have a method called Dig that takes an int and returns a string, it is a Digger, retroactively, whether it knew about the interface or not:

type Gopher struct{ Name string } func (g Gopher) Dig(cm int) string { return g.Name + " tunnels " + strconv.Itoa(cm) + "cm, humming" } type Backhoe struct{} func (Backhoe) Dig(cm int) string { return "BACKHOE DIGS " + strconv.Itoa(cm) + "CM. BACKHOE FEELS NOTHING" } func hire(d Digger) { fmt.Println(d.Dig(30)) } hire(Gopher{Name: "Gord"}) hire(Backhoe{})

The consequence is quietly enormous: you can write an interface after the types exist, and even for types you don't own — in someone else's library, in the standard library, in code written before you were hired. You define interfaces where you consume them, not where the types live.

Which is why Go people say: keep interfaces small. One method is normal. The most-used interface in the whole language, io.Writer, has exactly one. Big interfaces are a smell you'll learn to sniff.

You've been using this since chapter three without knowing. error is not magic; it is an interface with one method:

type error interface { Error() string }

Give anything an Error() string method and it can be an error. That's the whole envelope system, all the way down.

The empty interface, and getting your thing back out

An interface with no methods — interface{}, or its friendlier modern spelling any — is satisfied by literally everything, because everything can do nothing. It's the "I'll take whatever" box. Getting the real value back out requires you to ask, politely, and be prepared to be wrong:

var thing any = Gopher{Name: "Gord"} g, ok := thing.(Gopher) // ask: are you a Gopher? if ok { fmt.Println(g.Name) } switch v := thing.(type) { // or ask about several at once case Gopher: fmt.Println("a gopher named", v.Name) case Backhoe: fmt.Println("oh no") default: fmt.Println("unclear") }

Reach for any rarely. Modern Go has generics for the cases where you genuinely mean "a list of some type, I don't mind which" — func Largest[T int | float64](xs []T) T — and Gord's advice is to write ordinary boring code for a good long while before you go near them.

Chapter 7

A Thousand Gophers, One Tube

Goroutines, channels, select — the reason anyone learns this language.

Gord has brothers. Gord has an unreasonable number of brothers, and they are all currently digging, and there is a pneumatic tube running between them, and buckets of dirt keep arriving in it, and everyone seems calm.

Put the word go in front of a function call and it goes off and happens somewhere else while you carry on. That's a goroutine. It is not a thread — it's much cheaper, a few kilobytes, and Go's runtime shuffles hundreds of thousands of them across your actual CPU cores without asking you to think about it.

go dig(30) // off it goes. you are already on the next line.

Which raises the obvious problem: how do the brothers tell each other anything? Not by all scribbling in the same notebook and hoping. They use the tube.

tube := make(chan string) // a channel that carries strings go func() { tube <- "one bucket of dirt" // send: blocks until someone receives }() bucket := <-tube // receive: blocks until something arrives fmt.Println(bucket)

The arrow points the way the dirt travels. And notice the blocking — that's not a limitation, that's the synchronisation. Nobody needs a lock, because only one gopher holds the bucket at a time by construction. Go's slogan for this is worth paraphrasing badly: don't fight over one notebook; pass notes.

A channel you close() can still be drained, then yields zero values forever. for b := range tube loops until the channel closes — the tidiest way to say "until the digging is done".

Waiting for everyone to finish

var wg sync.WaitGroup for i := 1; i <= 3; i++ { wg.Add(1) go func() { defer wg.Done() fmt.Println("gopher", i, "is digging") }() } wg.Wait() // main waits here until all three call Done() fmt.Println("tunnel complete")

Add one, defer Done, Wait at the end. Three moves, and you'll use them constantly. Without that Wait, main returns, the program ends, and every goroutine is vaporised mid-sentence — the program does not wait for its own children.

Since Go 1.22 each loop iteration gets its own i, so the code above does what it looks like it does. In older Go you had to pass i in as an argument, and if you didn't, all three gophers shouted 4. A famous puddle to step in.

select: watching several tube mouths at once

select { case bucket := <-tube: fmt.Println("dirt arrived:", bucket) case <-time.After(2 * time.Second): fmt.Println("nobody sent anything. suspicious.") }

select waits on several channel operations and takes whichever is ready first. That's how timeouts, cancellation and "whoever answers first wins" all get written in Go, and it's why the language ended up running so much of the internet's plumbing.

There is a sync.Mutex for the times when a shared notebook really is the right answer — a counter, a cache. Use it without shame when it fits. But reach for the tube first.

Chapter 8

Ship the Tunnel

Tests, tools, and Gord's departure.

Testing in Go needs no library, no framework, no configuration file with opinions. A file ending in _test.go, a function starting with Test, and a small bird who checks your work:

// dig_test.go package main import "testing" func TestDig(t *testing.T) { got, err := dig(10) if err != nil { t.Fatalf("dig(10) returned error: %v", err) } if got != 10 { t.Errorf("dig(10) = %d, want 10", got) } }
$ go test ./... // run every test in the module $ go vet ./... // find the mistakes Nib is too polite to mention $ go fmt ./... // end all formatting arguments $ go build // one binary. no runtime. hand it to a stranger. $ go doc strings.Split // read the docs without leaving the terminal

No assertion library, you'll notice. You compare things with if and complain with t.Errorf. Yes, it's more typing. Yes, six months later you can still read it.

Where to go now

  • A Tour of Go — the official interactive tour, and genuinely the best next hour of your life.
  • Effective Go — how Go people actually write it. Short. Read it twice.
  • The standard library — go browsing. net/http, encoding/json, strings, time. You'll find things you were about to build.
  • Then build something small and real: a command-line tool that eats a file, or an HTTP server that answers in about twelve lines. Go rewards the small real thing.

The last page

Gord is packing his shovel. He does this by dragging it, which is not packing.

He wants to leave you with one thought, and it's the reason he came all this way to sit in your fruit bowl. Go is not a clever language. You are not going to write a line of Go that makes a stranger gasp. There's no syntax to be smug about at parties. Nib will keep declining your programs over unused turnips until the day you retire.

What you get instead is this: your programs compile in the time it takes to look up from the keyboard. They build into one file that runs anywhere. They do a hundred thousand things at once without you sweating. And a year from now, you will open code you have entirely forgotten writing, and you will simply — dully, gratefully — understand it.

That's the tunnel. Boring the whole way through, and it comes out exactly where the sign said.

Fin. There is dirt on your counter.
